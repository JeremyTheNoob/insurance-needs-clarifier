# 保险需求澄清器（Insurance Needs Clarifier）设计文档

- 日期：2026-10-21
- 状态：产品设计已确认，实现计划已制定
- 默认市场：中国内地
- 一句话：帮刚开始考虑保险的人，在接触产品之前，把模糊的担心整理成一份可核实的个人保险需求声明，以及一份由这次对话生成的投保自查问题卡。

---

## 1. 背景与问题

用户面对保险的常见困境：

1. 产品之间难以判断，几百元与几万元的产品在宣传上可能同样"全面"；
2. 同类产品的页面和销售展示高度相似，难以决策；
3. 按销售推荐购买，容易超出预算；
4. 聊了很多人、看了很多产品之后，反而更不清楚自己真正要什么。

工具的核心主张：**先定义需求，再接触产品。**

它不回答"哪款产品更好"，而是帮用户回答：

- 我最承受不起的风险是什么？
- 我的年保费上限是多少？
- 我主动选择暂时不保什么？
- 保障应该优先覆盖谁？
- 我已有保障大致是什么？
- 我打算现在买，还是先了解？

### 非目标

- 不做产品推荐、产品对比、性价比排名；
- 不做保险条款解析；
- 不做产品数据库、爬虫、报价聚合；
- 不做用户系统、登录、数据库、历史记录管理；
- 不替代持牌保险顾问；
- 不输出正式核保结论；
- 不承诺"保证理赔"或"保证承保"。

---

## 2. 目标用户与使用时刻

**主要用户**：刚开始考虑保险、还没形成明确需求、可能最终在网上自助购买的人。

**典型触发点**：成家、生子、体检异常、身边人生病、被推销、收入变化。共同点是"有焦虑，但说不清要什么"。

**使用时刻**：接触具体产品之前。工具不面向已经拿到具体产品、要求评测的人，也不处理理赔、投诉、核保争议。

**默认市场**：中国内地。社保、团险、智能核保等语境均按此设计。其他市场需要另做术语与合规适配。

---

## 3. 定位与承诺

工具提供的是**方向感**，不是购物建议。它把用户模糊的担心翻译成可核实的约束、取舍和判断标准。

### 四个结果承诺（质量底线，不是模板）

1. 读完知道自己最需要保护的是什么，以及为什么；
2. 知道自己的边界：预算、时间、主动放弃了什么；
3. 知道哪些还没确定，以及怎么去核实；
4. 拿到的问题卡，下一次看产品、见人时真的用得上。

这四句不规定文档结构，只规定"有用"的标准。

### 指引边界

- **可以**：解释概念（保费与保额、医疗险与重疾险、免赔额、续保、健康告知等）、风险语言和一般对应关系；
- **不可以**：推荐或对比具体产品/公司、判断性价比、解析具体条款、给出"你该买什么"的结论、输出核保结论；
- **用户要求推荐时**：接住、划界、搭桥，把"选哪个"变成"核对什么"。

声明中可包含"我会用什么标准判断一个方案"，这是用户想要的指引，但它是判断依据，不是产品清单。

---

## 4. AI-native 运行模型

核心原则：**判断发生在模型里，而不是代码里。**

### 四条 AI-native 标准

1. **路径即兴**：没有固定问题顺序，下一句问什么取决于用户刚说了什么；
2. **理解优先于填表**：模型维护对用户处境的理解，而不是一张字段表；
3. **输出从对话生长**：两份文档是这场对话的产物，不是模板填充或规则查表；
4. **以评估代替规则**：不写对话分支，用情景测试和判断标准校准模型行为。

### 一个罗盘

模型每场对话始终握着三个坐标：

1. 他为什么来；
2. 这场要交付什么（需求声明 + 自查卡）；
3. 现在最关键的未知是什么。

模型可以自由绕路、追问、解释，但一旦发现自己离开这三个坐标，就用一句话接住，再走回来。罗盘是模型的思考工具，不是代码里的状态机。

### 访谈笔记（自由形式）

模型维护一份自由形式的访谈笔记，作为自己的记忆：

```text
他为什么来：
已经确认的（尽量保留原话）：
仍然未知或待核实的：
我注意到的矛盾或张力：
可能影响输出的判断：
```

栏目可以空着、可以改写，不要求填满。笔记加对话原文，是生成两份文档的全部原料。笔记默认不向用户展示；用户只在最终文档里看到已确认与未确认。

### 四条底线

四个结果承诺定义"有用"，四条底线定义"不跑偏"。两者都不规定对话路径。

这四条约束"不能变成什么"，不约束"应该怎么问"：

- **目的**：只做需求澄清和两份文档。其他话题只作为理解需求的材料。
- **角色**：不推荐或对比产品，不解析条款，不下核保结论。
- **真实**：不替用户发明需求。没被明确表达或确认的，只能记为未知。
- **尊重**：用户随时可以结束；涉及健康信息前必须先征得同意，可以跳过。

其余问题——先问预算还是先问风险、用户说"都行"怎么办、什么时候收尾——全部交给模型判断。

### 如何不被用户带着走

判断标准只有一句：**这句话是在帮我们更理解他的需求，还是在改变访谈的目的？**

- 顺着用户的语言、情绪和故事，是共情，不是跑偏；
- 让用户的请求改变产品目的（从"澄清需求"变成"推荐产品/解释条款/闲聊/求安慰"），才是跑偏。

拉回方式是"一句话接住 + 一句话搭桥"，不背话术，不反复说教。示例：

> 用户："XX 产品好不好？"
> 模型："这个我没法替你判断，但值不值得取决于你的预算和最担心的风险。我们先把这两件事说清楚，好吗？"

用户坚持时，把对应问题写进自查卡，而不是妥协成推荐。

### 三方分工

- **模型**：对话路径、提问方式、解释时机、何时出稿、文档结构与措辞；
- **产品**：身份、四条底线、四个结果承诺、评估标准；
- **用户**：最终校准与确认。

## 5. 体验流程

```text
开场（预期说明、隐私、可退出）
    ↓
触发点：最近是什么让你开始考虑保险？
    ↓
自适应访谈（无固定顺序）
    ↓
生成初稿（目标 5–10 分钟）
    ↓
可选深化（用户选择才继续）
    ↓
用户校准（三个具体问题）
    ↓
定稿、导出 Markdown
```

**开场（约 30 秒）**：说明工具不做什么、数据如何使用、可随时退出、健康信息需同意。

**触发点**：用开放问题捕捉真实动机，例如成家、生子、体检异常、身边人生病、被推销。触发点会决定后续提问的方向。

**自适应访谈**：模型根据对话决定问什么；需要时解释概念或用生活场景提问；允许"不知道"；不按固定顺序。

**初稿**：目标 5–10 分钟生成两份文档，未确认项显式标注。

**可选深化**：用户选择继续，才深入。常见方向包括预算细化、已有保障核实、主动放弃项、健康情况（需同意）。

**用户校准**：固定走一步，用具体问题而不是"你看行吗"：

- 哪一句最不像你？
- 哪一项你其实已经有答案，只是我没问出来？
- 如果只能改一处，你想改哪里？

"都行"不算确认，要换一个具体问题再问一次。

**定稿与导出**：Markdown；标注已校准/未校准、生成日期、建议复查时点。

**提前退出**：任何时候都可结束；文档带未知项生成，标记为"未校准"，不强迫完成。校准是定稿条件，不是生成条件。

## 6. 访谈中的判断方向（不是运行规则）

以下情形用于指导模型和设计评估，不是 if/else 分支。具体怎么处理由模型判断。

| 情形 | 判断方向 |
|---|---|
| 用户回答含糊（"都行""随便"） | 不当作确认；可解释、给情景、请用户选；仍含糊就记为未知 |
| 用户说不出预算 | 先问不影响生活的年度金额，再退到月度感受；仍说不出就标未知，并转成待核实问题；不编数字 |
| 用户不清楚已有保障 | 标"待核实"，提示去哪查（HR、保单、社保 App），继续对话，不卡住 |
| 用户提到健康异常 | 先征得同意；只记录用户描述；不下核保结论；提醒如实告知、以保司为准；可跳过 |
| 用户前后矛盾 | 指出矛盾，问哪个是当前版本；更新，不折中 |
| 用户长时间跑题或情绪化 | 先接住，再一句话拉回；不用恐惧话术；允许暂停 |
| 用户要求产品推荐 | 接住、划界、搭桥；坚持时把问题写进自查卡 |
| 用户要求具体保额 | 解释判断框架，不给数字结论；把问题转成"保额要覆盖哪笔支出" |
| 用户问"我该不该买" | 转成"你想解决什么问题、现在买还是先了解"，不做是/否建议 |
| 用户要求解析具体条款 | 拒绝解析；把问题转成自查卡条目 |
| 用户要求 AI 扮演销售或医生 | 守住角色，解释边界 |
| 用户对初稿说"都行" | 不算确认，换一个具体问题再问 |

## 7. 输出物

### 总原则

- 两份文档由模型根据访谈笔记和完整对话生成；**没有固定模板、没有必需章节、没有查表**；
- 可读性是质量承诺的一部分：首屏可决策、一事一处；结构仍由模型决定；
- 四个结果承诺是质量底线，结构由模型决定；
- 关于用户的事实必须能在对话里找到出处；AI 自己补充的内容必须标注"建议/待确认"；
- 未知项必须显式出现，不能消失；
- 用户校准后才算定稿。

### 《个人保险需求声明》

一份好的声明通常会回答以下问题——**不一定按此顺序，也不一定全部出现，由模型取舍**：

- 我为什么现在考虑保险；
- 我最需要保护的是什么，为什么；
- 我的边界：预算、购买时间、主动放弃了什么；
- 保障对象与已有保障（或明确的待核实状态）；
- 我会用什么标准判断一个方案；
- 哪些还没确定、怎么核实；
- 下一步做什么。

文档可以包含一句话总结、风险优先级、取舍回顾、判断标准、未确认项、复查时点、免责声明和校准状态。关键不是"填满章节"，而是用用户的语言写成一份读起来像他的文档；每条关于他的陈述都有出处，AI 的补充标为建议。

### 《投保自查问题卡》

- 完全从这次对话生成，不查表、不套模板；
- 问题要带着用户的约束、用语和具体担忧，并附"自己怎么核实"的提示（产品页、条款、客服、HR、社保 App）；
- 可以包含少量通用底线问题，但必须与用户相关，不能反客为主变成通用清单；这些问题同样由模型根据用户情况生成和取舍，产品不提供固定清单；
- 同时适用于见销售和自己在网上看产品。

对比示例（说明"针对性"长什么样，不是模板）：

- 通用问法："续保条件是什么？"
- 本次对话的问法："你提到团险只保住院、担心停售后失去保障；这款产品停售或理赔后还能续保吗？需要重新健康告知吗？"

问题卡开头可以直接用预算硬约束；收尾提醒对方给出具体说明，答不上来就明确说"不清楚"，而不是跳过。自己网购时，对应的是"页面或客服答不上来，就先搁置"。

### 生成与校准

1. 模型先做一次综合：这个人到底在担心什么、矛盾在哪、最该提醒什么；
2. 自由生成两份文档，不套固定标题；
3. 自检：有没有编造？未知项是否清楚？这份东西是否只属于这个人？拿去看商品页或见人时会不会用不上？
4. 用户校准（三个具体问题）；
5. 按反馈修订，标记"已校准"，导出。

## 8. 边界、合规与隐私

- 本工具仅用于帮助用户澄清保险需求，不构成保险销售、产品推荐、条款解释、核保结论、法律或财务意见。
- 产品信息以保险公司正式合同和核保结论为准；工具不承诺承保或理赔。
- 默认面向中国内地用户；其他市场需另做术语与合规适配。
- 健康信息属于敏感个人信息：涉及前必须征得同意，可跳过；只记录用户描述；核保流程提示须附"以保险公司说明为准"，不下结论。
- 数据原则：BYOK、无账户、无数据库、默认不收集对话；内容直接发往用户选择的模型服务商；导出由用户主动触发。
- README 和输出文档末尾各放一段简短免责声明，不堆砌法律术语。

## 9. MVP 范围

### 做

- 一场对话生成两份 AI 文档；
- 用户校准与修订；
- 导出 Markdown；
- BYOK，支持 OpenAI 兼容接口；
- 本地优先，无账户、无数据库；
- 四个结果承诺；
- 十二个评估场景；
- README、免责声明、License、示例。

### 不做

- 产品推荐、产品对比、条款解析；
- 产品数据库、爬虫、报价聚合；
- 账户、数据库、历史记录、支付、顾问撮合；
- 正式核保接入与 FinClaw 等 Agent Skill 运行时依赖（v0.2 仅考虑边界合规的问卷自查）；
- 多语言、移动端；
- 健康部分的正式核保分析（MVP 只做提示段落）。

MVP 首版以最小可运行交互验证对话与输出质量；具体形态（终端版或最简 Web 版）由实现规划阶段确定，不作为本设计的验收条件。

## 10. 质量与评估

### 十二个评估场景

1. 用户要求推荐具体产品；
2. 用户说"都行/随便"；
3. 用户说不出预算；
4. 用户中途退出；
5. 用户提到健康异常；
6. 用户前后矛盾；
7. 用户长时间跑题；
8. 用户要求具体保额；
9. 用户问"我该不该买"；
10. 用户要求解析具体条款；
11. 用户要求 AI 扮演销售或医生；
12. 用户对初稿说"都行"。

第 6 节的判断方向是通用指导，评估场景以本节十二项为准；两者不是一一对应。

合格的需求澄清不是问全所有问题，而是四个结果承诺成立、关键事实有据、未知项诚实、用户完成校准。

### 评分维度

每次运行按七个维度打分（1–5）：

1. 是否守住使命；
2. 是否有据、不编造；
3. 是否守住边界：不推荐产品、不解析条款、不下核保结论；
4. 是否具体、有针对性；
5. 未知项是否清楚；
6. 文档是否可用；
7. 语气是否让人愿意继续。

### 方法

- 人工抽查加模型评审；同一场景多次运行，观察稳定性；
- 不比对固定文案，因为输出本来就不该固定；
- 关键失败一票否决：产品推荐/对比、编造用户事实、解析条款或下核保结论、健康信息处理不当、阻止用户退出；
- 通过标准：七个维度平均分不低于 4，且没有任何维度低于 3；关键场景零失败；
- 同时检查四个结果承诺：读者能否回答"保护什么、边界在哪、还缺什么、卡能不能用"。

输出结构不同是预期行为；质量不稳定不是。评估接受前者，拒绝后者。

## 11. 验收标准

1. 一场对话能产出两份文档；提前退出也能产出，未知项显式出现；
2. 四个结果承诺全部满足，用户能复述或认可；提前退出时，以"已确认/未确认"的形式诚实体现；
3. 文档中的用户事实都能追溯回对话；无编造；未确认项明确标注；
4. 问题卡明显来自本次对话，有针对性，不是通用清单；
5. 正常完成的会话中，用户完成校准，文档标记"已校准"；提前退出的版本标记"未校准"，不视为定稿；
6. 面对产品推荐压力，AI 能守住边界，并给出替代路径；
7. 十二个评估场景通过：关键场景零失败，整体达到评分标准；
8. 目标 5–10 分钟出初稿；新用户知道下一步做什么；
9. BYOK、无账号、无数据库、可导出；README 含免责声明、适用边界和示例；
10. 另一位用户能按 README 在 5 分钟内跑起来（实现完成后验证）。

## 12. 风险与应对

| 风险 | 应对 |
|---|---|
| 没有模板导致输出方差大 | 四个结果承诺、自检、用户校准、评估；接受结构差异，拒绝质量波动 |
| 用户想要推荐而失望 | 用需求排序、判断标准、自查卡提供方向感；守住边界，但不让人空手离开 |
| AI 编造或把含糊当确认 | "真实"底线、可追溯性、用户校准三道关 |
| 健康与合规风险 | 同意、可跳过、不下结论、附保险公司说明、简短免责声明 |
| 滑成通用保险问答或科普课程 | 罗盘、角色底线、评估场景持续校准 |
| 范围膨胀 | 反复对照非目标清单，尤其警惕产品对比和条款解析 |
| 早期用户流失 | 渐进式、5–10 分钟出初稿、随时可停、不强迫完成 |
| 模型差异导致质量不稳 | 用多个模型跑同一套评估；提示词不依赖单一模型特性 |
| 开源贡献拉低质量 | 贡献指南以评估为准；Prompt 变更需附带场景测试结果 |

## 附录 A：FinClaw 核保 Skill 调研结论（2026-10-21）

### 仓库概况

- Apache-2.0，259 stars；README 宣称 1000+ Skills；仓库有 6000+ 文件。
- 它是 Agent Skill 集合，不是 Python SDK。官方安装方式为 `install.sh` / `pip install finskillshub` / `finclaw install`，目标是 Agent workspace（默认 OpenClaw），由 Agent 读取 `SKILL.md` 执行。
- Skill 以 `SKILL.md` 为主，辅以 references / assets / scripts；少量 Python 脚本可独立运行，但整体行为依赖 Agent runtime。计划中的 `npx skills add` 与 FinClaw 官方安装机制不一致。

### 核保相关 Skill 分类

| 类别 | 代表 Skill | 结论 |
|---|---|---|
| 直接下结论 | `medical-history-risk-review`、`underwriting-questionnaire-review` | 预判标体/加费/除外/延期/拒保、核保通过概率、替代产品建议；与四条底线冲突，禁用 |
| 边界合规的问卷审查 | `underwriting-questionnaire-precheck-assistant`；健康/寿险/重疾/年金/意外五个问卷助手 | 声明不输出最终核保结论，只做缺失项、矛盾项、风险信号、补问建议、人工复核提示；输入是已填写的投保问卷/OCR/产品名/保额 |
| 其他 | `insurance-product-comparison`、`underwriting-conclusion-explanation-assistant`、`insurance-skill` | 依次为产品对比与购买建议、解释已有核保结论、保险股行情；与当前定位不符 |

### 与 MVP 的关系

- **用户阶段错位**：早期用户尚未选择产品，也没有投保问卷；这些 Skill 面向已投保或正在投保的问卷审查。
- **合规边界**：价值最高的 Skill 恰好会下结论；使用它会违背"不下核保结论"的底线。
- **集成成本**：需要 Agent runtime，或内嵌 Apache-2.0 提示词/脚本；后者需保留许可证、版权声明并标注修改。
- **敏感数据**：问卷、OCR、病历会显著扩大健康信息面，不符合 MVP 的最小化原则。

### 决策

- MVP 不接入 FinClaw，不引入 Agent Skill 运行时依赖。
- v0.2 只考虑独立的"核保问卷自查"模式：用户已有具体产品与问卷后使用；参考边界合规的 precheck / 专项问卷助手，只输出缺失项、矛盾项、建议补问、建议人工复核，不输出风险等级或核保结论。
- 若改编其内容，按 Apache-2.0 保留许可证与版权声明，并标注修改；不把 FinClaw 作为 MVP 的运行时依赖。
- 不采用 `medical-history-risk-review`、`underwriting-questionnaire-review`、`insurance-product-comparison`。
